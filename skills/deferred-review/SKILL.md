# Deferred Review

Обработать каждый finding из финального отчёта rr-loop, который не был реализован: любого статуса, отложенный или оставшийся после исчерпания лимита rr-loop, а также каждый пункт «требует внимания человека». Получить решения человека, выполнить принятые исправления, создать согласованные задачи и опубликовать итог в трекере.

## Предусловия

1. Прочитать `docs/agents/issue-tracker.md`.
2. Убедиться, что доступны скилл `code-review` и субагенты `reviewer` и `reviser`.
3. Взять ID текущей задачи из контекста запуска `/rr-loop`.

## Фаза 0. Сбор findings

1. Прочитать финальный отчёт rr-loop; если его нет в контексте, извлечь из последнего комментария текущей задачи в трекере.
2. Собрать все нереализованные findings любого статуса, в том числе:
   - отложенные findings;
   - findings, не реализованные из-за лимита итераций rr-loop;
   - пункты «требует внимания человека»;
   - findings из незавершённого последнего review-revise шага.
3. Исключить только findings, явно помеченные как реализованные или отклонённые с зафиксированным обоснованием.
4. Если список пуст, перейти к Фазе 3.
5. Зафиксировать `BASE` командой `git rev-parse HEAD`.
6. Загрузить текущую задачу и связанные задачи из трекера.

## Фаза 1. Опрос человека

Для каждого finding показать полностью: статус, файл и строку, суть, причину, предлагаемое исправление и источник (отложен / лимит rr-loop / требуется внимание человека).

Задать все вопросы за одну итерацию. Использовать любой доступный инструмент для вопросов; предпочесть инструмент, который принимает несколько вопросов одним вызовом. Если такого инструмента нет, задать вопросы текстом одним сообщением.

Для каждого finding предложить:

1. **Исправить сейчас** — внести правку в текущей сессии.
2. **Создать задачу в трекере** — создать связанную задачу с полным контекстом.
3. **Отклонить** — не исправлять; запросить и записать причину.

Сформировать списки: **к исправлению**, **новые задачи**, **отклонённые**. Не считать finding обработанным до получения явного ответа или явного решения человека.

## Фаза 2. Выполнение решений

### Создание задач

Для каждого finding из списка **новые задачи** создать задачу согласно `docs/agents/issue-tracker.md`:

- `summary`: краткое название до 70 символов;
- `description`: полное описание finding, его источник, файл и строка, контекст родительской задачи, текущая ветка и `BASE SHA`;
- тип `Task`, приоритет, соответствующий severity finding, и стадия `Backlog` — по схеме полей проекта;
- связь `relates to` с текущей задачей и с упомянутыми задачами;
- тег `deferred-from-rr-loop`.

Зафиксировать ID, summary и URL созданной задачи.

### Реализация и проверка

Если список **к исправлению** не пуст:

1. Передать findings субагенту `reviser` в формате отчёта reviewer.
2. Принять отчёт ревизора: исправленные и отклонённые findings с причинами.
3. Если ревизор отклонил finding, зафиксировать его как **отклонённый ревизором**; если причина требует решения человека — добавить в **требует внимания человека**.
4. Закоммитить принятые правки: `chore: обработаны findings rr-loop <ID задачи>`.
5. Запустить `code-review` против `BASE` по осям Standards и Spec текущей задачи.
6. При BLOCKER или MAJOR передать findings ревизору и повторить review-revise, максимум две итерации.
7. Findings, оставшиеся нереализованными после лимита повторных итераций, добавить в **требует внимания человека**. Не объявлять их отклонёнными без явного обоснования.

## Фаза 3. Предложение завершения

После Фазы 2 проверь: нет ли нереализованных и неотклонённых findings и нет ли пунктов **требует внимания человека**.

Только если оба условия выполнены, задай человеку один вопрос: выполнить ли завершение задачи — смержить текущую ветку в родительскую git-ветку, пометить задачу в трекере завершённой и закрыть текущий git worktree, если он есть. Использовать любой доступный инструмент для вопросов; предпочесть поддерживающий несколько вопросов инструмент. Не выполнять эти действия без явного подтверждения.

Если человек подтвердил, выполнить действия в указанном порядке, соблюдая инструкции `docs/agents/issue-tracker.md` и безопасно закрыв только текущий worktree. Если отказался или отложил — зафиксировать это в отчёте.

## Фаза 4. Итоговый отчёт

Опубликовать в текущей задаче и вывести пользователю Markdown-отчёт:

```markdown
## Итоговый отчёт: обработка findings rr-loop

**Задача:** <ID текущей задачи>
**Дата:** <текущая дата>
**BASE:** <BASE SHA>
**HEAD:** <HEAD SHA>

### Рассмотрено findings: <количество>

#### Исправлено
- [<СТАТУС>] <file>:<line> — <краткое описание> → FIXED

#### Создано задач
- <ID> — <summary> — <URL>

#### Отклонено
- [<СТАТУС>] <file>:<line> — <причина>

#### Требует внимания человека
- [<СТАТУС>] <file>:<line> — <суть>

### Повторное ревью
**Итераций:** <количество>
**Вердикт:** <APPROVE / CHANGES_REQUESTED>

### Завершение задачи
<подтверждено и выполнено / отложено / недоступно из-за незакрытых findings>

### Коммиты
- <SHA> — <сообщение>
```

## Правила

- Не ограничиваться MINOR и не ограничиваться отложенными findings.
- Не использовать и не требовать конкретный инструмент для вопросов.
- Не создавать или не закрывать задачу без явного решения человека.
- Минимизировать изменения вне принятых findings, не коммитить секреты и использовать семантические префиксы коммитов.
