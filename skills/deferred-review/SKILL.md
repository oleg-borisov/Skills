# Deferred Review

Интерактивная обработка отложенных замечаний после завершения цикла rr-loop.
Агент проходит по каждому отложенному MINOR и пункту "требует внимания человека",
задаёт человеку вопрос с вариантами действий, реализует выбранные правки,
прогоняет review-revise по исправленному коду и публикует итоговый отчёт
в трекер с привязкой к текущей задаче.

## Условие запуска

Скилл запускается **вручную пользователем** после того, как rr-loop выдал
финальный отчёт с отложенными MINOR или пунктами «требует внимания человека».

ID текущей задачи берётся из контекста — он был передан при запуске `/rr-loop`.

## Предусловия

1. `docs/agents/issue-tracker.md` — описание трекера.
2. Скилл `code-review` доступен.
3. Субагенты `reviewer` и `reviser` доступны.

## Фаза 0. Загрузка отложенных замечаний

1. Определи ID текущей задачи из контекста (был передан при запуске `/rr-loop`).
2. Прочитай финальный отчёт rr-loop или извлеки из последнего комментария задачи в трекере.
3. Извлеки все отложенные MINOR-замечания и пункты «требует внимания человека».
4. Если замечаний нет — останови выполнение и сообщи пользователю.
5. Зафиксируй BASE (`git rev-parse HEAD`) перед началом работы.
6. Загрузи информацию о текущей задаче из трекера согласно `docs/agents/issue-tracker.md`,
   включая связанные задачи.

## Фаза 1. Интерактивный опрос

Для **каждого** отложенного замечания:

1. **Покажи замечание** полностью: статус, файл, строка, суть, причина, предложенное исправление.
2. **Задай вопрос** с вариантами через инструмент `question`:
   - **Исправить сейчас** — внести правку в текущей сессии
   - **Создать задачу в трекере** — завести отдельную задачу, связанную с текущей
   - **Пропустить** — не исправлять, не заводить задачу
3. **Обработай ответ**:
   - Если "Исправить сейчас" → добавь замечание в список **к исправлению**.
   - Если "Создать задачу в трекере" → добавь в список **новых задач** (с полным описанием замечания, контекстом, ссылкой на файл и строку).
   - Если "Пропустить" → добавь в список **пропущенных**.
**Все вопросы задать за одну итерацию. Если подходящего инструмента нет, то задать текстом**
Пример форматирования вопросов
```
❓ **В1** - **<Заголовок вопроса>**: <Тело запроса, может быть несколько параграфов, включая несколько вариантов ответа>

➡️ <Рекомендуемый ответ>
```

После опроса по всем замечаниям получишь три списка: к исправлению, новые задачи, пропущенные.

## Фаза 2. Создание задач в трекере

Для каждой задачи из списка **новых задач**:

1. Создай задачу в трекере согласно `docs/agents/issue-tracker.md`:
   - `summary`: краткое название замечания (до 70 символов)
   - `description`: полное описание в Markdown:
     ```
     ## Замечание из rr-loop
     [MINOR] file:line — суть / почему / как исправить
     
     ## Контекст
     Родительская задача: <ID текущей задачи>
     Ветка: <текущая ветка>
     Коммит: <BASE SHA>
     ```
   - Используй схему полей проекта для установки типа (Task), приоритета (Minor) и стадии (Backlog).
2. Свяжи новую задачу с текущей через `relates to`.
3. Если в описании замечания упоминаются другие задачи — свяжи их тоже через `relates to`.
4. Добавь тег `deferred-from-rr-loop`.

Зафиксируй список созданных задач: ID, summary, URL.

## Фаза 3. Реализация исправлений

Если список **к исправлению** не пуст:

1. Запусти субагент `reviser` через task (тип `general`):
   - Передай список замечаний в том же формате, что reviewer выдаёт.
   - Ревизор должен принять каждое замечание и внести правки.
2. Получи отчёт ревизора: что исправлено, что отклонено (с причинами).
3. Если есть отклонённые замечания — добавь их в список **требует эскалации**.
4. Закоммить правки с сообщением `chore: применены отложенные MINOR из rr-loop <ID задачи>`.

## Фаза 4. Повторное ревью

Если были внесены исправления (Фаза 3):

1. Загрузи скилл `code-review` через инструмент `skill`.
2. Запусти двухосевое ревью против BASE:
   - `git diff BASE...HEAD`
   - Spec-ось: текущая задача как источник спецификации (прочитай её из трекера).
   - Standards-ось: документированные стандарты + baseline code smells.
3. Запусти обе оси параллельно через task (тип `general`).
4. Агрегируй отчёты обеих осей.
5. Классифицируй новые findings по статусам [BLOCKER] / [MAJOR] / [MINOR].
6. Если есть BLOCKER или MAJOR:
   - Запусти субагент `reviser` повторно с новыми замечаниями.
   - Повтори Фазу 4 (максимум 2 итерации повторного ревью).
7. Если после 2 итераций остались BLOCKER/MAJOR — добавь в список **требует эскалации**.

## Фаза 5. Финальный отчёт

Сформируй итоговый отчёт в Markdown:

```markdown
## Итоговый отчёт: обработка отложенных замечаний

**Задача:** <ID текущей задачи>
**Дата:** <текущая дата>
**BASE:** <BASE SHA>
**HEAD:** <HEAD SHA после правок>

### Обработано замечаний: <общее количество>

#### Исправлено в текущей сессии: <количество>
- [MINOR] file:line — краткое описание → FIXED
...

#### Создано задач в трекере: <количество>
- <ID задачи> — <summary> — <URL>
...

#### Пропущено: <количество>
- [MINOR] file:line — краткое описание → SKIPPED
...

#### Требует эскалации: <количество>
- [СТАТУС] file:line — суть / почему требует эскалации
...

### Повторное ревью

**Итераций:** <количество>
**Вердикт:** <APPROVE / CHANGES_REQUESTED>

#### Новые findings (если есть):
- [СТАТУС] file:line — суть
...

### Коммиты
- <SHA> — <commit message>
...

### Связанные задачи
- <ID> — <summary> — <тип связи>
...
```

Опубликуй отчёт комментарием в текущую задачу согласно `docs/agents/issue-tracker.md`.

Выведи отчёт пользователю.

## Правила

- Каждое замечание обрабатывай строго по одному: показал → спросил → записал ответ → следующее.
- Варианты ответа должны быть чёткими, без "Other" (включи `custom: true` в question, если нужно).
- При создании задач всегда указывай контекст: родительская задача, ветка, коммит, файл, строка.
- Не коммить секреты.
- Коммиты с семантическими префиксами (chore: для deferred-правок).
- Минимизируй изменения вне замечаний.
- Если ревизор отклонил MINOR — это нормально, добавь в отчёт как "отклонено ревизором".
- Если ревизор отклонил что-то из "требует внимания человека" — эскалируй в отчёт.
