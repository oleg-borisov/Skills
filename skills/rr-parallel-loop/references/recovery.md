# Recovery rr-parallel-loop

## Возобновление

1. Для существующего нетерминального ledger предложи resume или явный reset. Без решения не удаляй данные и не запускай реализацию повторно. Сканируй ledgers rr-parallel-loop по task/spec и связанным branch/worktrees и его claim directory. Два активных владельца одной работы в этом workflow → HUMAN_ATTENTION. Reset не означает разрешение удалить незакоммиченный код.
2. Прочитай state.json, актуальные OPEN records и хвост после findings_seq. Старую историю читай только при расхождении. Неполная запись не доказывает действие.
3. Сверь spec/standards hashes, BASE, integration ancestry, task branches/cwd, реальный HEAD, worker liveness, PR/transition state и pending intents. Устаревшие notes переиспользуй только после сверки sources worker'ом. Изменение graph/requirements требует согласования нового плана, необъяснимый Git drift → HUMAN_ATTENTION.
4. RUNNING + живой worker → снова наблюдай его, не dispatch дубликата. Неизвестная liveness → HUMAN_ATTENTION. Завершившийся worker без checkpoint → восстанови результат по final handoff и branch HEAD. При техническом сбое/неполном отчёте используй правила ниже; dirty files сами по себе не означают потерю ownership или необходимость нового решения человека.
5. Merge intent без result: если точный source_sha уже ancestor integration tip и изменение tip объясняется этим merge, восстанови INTEGRATED, не merge повторно. Если merge ещё в процессе, при отсутствии живого writer прерви только собственную подтверждённую операцию и продолжи conflict path. Необъяснимые parents/другой tip → HUMAN_ATTENTION.
6. Внешнее действие без result сначала сверяй с tracker/PR/host. Неизвестный исход → HUMAN_ATTENTION, не слепой повтор. Успешные действия не повторяй. Gate/review evidence относится только к сохранённому HEAD и входам; после переписывания истории сбрось coverage и считай BASE для нового review от актуального parent tip, сохранив origin BASE отдельно.
7. Продолжай сохранённую фазу/counters/fixed points и pending_action после ответа, не возвращайся в Implement автоматически. Перед повторным dispatch докажи выход предыдущего worker и его пишущих subprocesses. Обычно checkout должен быть чистым. Для передачи незавершённой попытки другому worker сохрани HEAD, inventory путей и hashes staged/unstaged/untracked содержимого, включая удаления, без чтения product patch controller'ом. Сверь происхождение правок, запиши нового owner и snapshot ref в directives_path. Worker проверяет snapshot до первого изменения; расхождение/неизвестное происхождение → HUMAN_ATTENTION. Продолжение той же попытки тем же owner следует основному skill. Dirty integration/Verify/Review по-прежнему запрещены.

## Технически незавершённая попытка

- Capacity/transport failure при подтверждённом выходе worker, неизменных requirements и известном единственном owner: продолжи сохранённую попытку без повторного разрешения. Предпочитай тот же агент с его контекстом; иначе fresh агент той же named role с передачей dirty по п. 7. Не меняй модель/роль в обход настроек. Неизвестный исход tool/check сначала сверяй, а не повторяй.
- Готовый commit без handoff или неполный JSON: продолжение только для восстановления отчёта из имеющихся evidence. Controller сохраняет полученный JSON сам. Повторная реализация и повтор успешных checks с теми же HEAD/входами не нужны; отсутствующее evidence нельзя выдумывать.
- Сохраняй технические retries в dispatch operations по task/phase; максимум два автоматических продолжения одной незавершённой попытки, включая восстановление отчёта. Затем HUMAN_ATTENTION с причиной. Они не расходуют счётчик product RED/repair; build/test failure обрабатывается обычным Verify, не этим retry.
- BLOCKED из-за адресации refs/вызова checks можно продолжить после подтверждённого устранения причины без изменения проверяемых входов. Передай исправленные refs/способ запуска и сохранённые результаты. Неподтверждённая среда, чужие изменения, требования вне scope или неизвестная liveness → HUMAN_ATTENTION. Успешное восстановление отчёта не заменяет gate/review.
